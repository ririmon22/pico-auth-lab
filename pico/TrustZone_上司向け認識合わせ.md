# TrustZone活用に関する現状整理と今後の方針

**対象**：ZCU106（Zynq UltraScale+ MPSoC）を用いたベアメタル検証  
**作成日**：2026年10月14日  
**目的**：実証済み事項、今後の開発範囲、Arm／OSS／SoCが提供する機能と自作部分の境界について認識を合わせる。

## 1. 要約

今回の取り組みは、**既製のTrusted OSを導入すること自体が目的ではなく、SoCのTrustZone関連機構を利用して、秘密情報や重要処理をNon-secure側から分離できるかを検証するもの**です。

現在、Cortex-A53のEL3からNon-secure EL1への遷移、保護前のDDR共有アクセス、XMPUのリージョン設定・読み戻し、例外の記録まで確認しています。一方、**XMPUによってNon-secure側からのアクセスを実際に拒否できることは、まだ実証していません**。また、認証・鍵管理・Secure APIは未実装です。

**ベアメタル環境では、OP-TEEなどの既製Trusted OSは必須ではありません。** ただし、Non-secure側からSecure側の機能を呼び出す場合は、SMC受付や状態切り替えなど、必要なSecure Monitor機能を自作するか、TF-A等の既存実装を利用する必要があります。OSの有無と、認証・認可の要否は別問題です。

## 2. 現在どこまでできているか

| 項目 | 状態 | 確認内容・限界 |
|---|---|---|
| EL3での実行 | 確認済み | Cortex-A53の例外レベルを確認 |
| EL3→EL1遷移 | 確認済み | Secure状態からNon-secure状態へ遷移するよう構成し、EL1での実行を確認 |
| DDRへのアクセス | 確認済み | 保護前にEL3とEL1から同じアドレスの値を読み取れた |
| XMPUリージョン設定 | 設定・読み戻し済み | 対象領域のレジスタ値が意図した値であることを確認。ただしアクセス制御の有効性は未証明 |
| EL1例外ハンドラ | 確認済み | 意図的なData Abortを発生させ、原因・アドレス・命令位置を記録 |
| XMPUによるアクセス拒否 | **未検証** | 今後の最優先事項 |
| SMCによる往復呼び出し | 未実装 | EL3側の受付・復帰処理が必要 |
| 認証・認可／鍵管理 | 未設計・未実装 | 用途と脅威モデルの合意が必要 |
| Secure Boot／製品レベルの信頼性 | 未検証 | 起動経路、署名検証、デバッグ制限等を別途検討 |

**現時点の評価**：TrustZoneの基本的な制御と実験環境は成立しています。ただし、「安全な隔離領域が完成した」「秘密鍵を安全に保護できる」と結論づける段階ではありません。

## 3. 技術要素の役割分担

| 要素 | 区分 | 主な役割 | 今回の位置づけ |
|---|---|---|---|
| **SoC**（Zynq UltraScale+ MPSoC） | ハードウェア製品 | CPU、DDR制御、周辺回路、セキュリティ機能を集積 | 実験対象の基盤 |
| **Arm TrustZone** | アーキテクチャ／ハードウェア機構 | SecureとNon-secureの実行・アクセス属性を分離 | 分離の基礎機構 |
| **XMPU／XPPU** | SoC内ハードウェア | メモリ／周辺機器へのアクセスを制御 | DDRのXMPUを検証中 |
| **Secure Monitor** | EL3で動くソフトウェアの役割 | SMC受付、例外処理、状態切り替え等 | 必要な最小機能を自作可能 |
| **TF-A**（Trusted Firmware-A） | 既製ファームウェア | EL3ランタイム（BL31）や起動処理等を提供 | 採用候補。今回の実験では未使用 |
| **OP-TEE** | 既製Trusted OS | Secure側アプリ、暗号API、セッション、ストレージ等 | 採用候補。今回の実験では未使用 |
| **Linux／RTOS** | 通常側OS | アプリ実行、ドライバ、プロセス管理等 | 現在は使用していない |
| **自作Secureサービス** | アプリケーション設計 | 秘密鍵の使用、署名、認可等の業務機能 | 今後の開発候補 |

### 混同しやすい点

- **TrustZone ≠ OP-TEE**：TrustZoneは分離の基盤、OP-TEEはそれを利用するソフトウェアの一つです。
- **Secure Monitor ≠ 認証アプリ**：Monitorの中心は例外・状態切り替えです。ユーザー認証や要求の認可は別の機能です。
- **TF-A ≠ OP-TEE**：TF-AのBL31は主にEL3、OP-TEEは代表的にはSecure EL1で動作します。
- **ベアメタル ≠ セキュリティ検証不要**：OSがなくても、Non-secureコードが改変される脅威を想定するなら、Secure側の要求検証は必要です。

## 4. 想定するシステム構成

### A案：今回の検証を発展させる最小構成（自作）

```text
Non-secureベアメタルアプリ（EL1）
       │
       │ SMC：Secure側サービスへの要求
       ▼
自作Secure Monitor／最小サービス（EL3）
       │
       ├─ 引数・要求内容の検証
       ├─ 必要な権限判定
       └─ Secure側の秘密情報を利用した処理
       │
       └── ERETで結果を返す

SoCハードウェア：TrustZone属性／XMPUによるアクセス分離
```

**利点**：構成が小さく、何を保護し、どこで状態が切り替わるかを把握しやすい。実験・学習・限定用途に適します。  
**課題**：SMC、例外、レジスタ保存、入力検証、認可、鍵管理などを自分たちで正しく設計・実装・検証する必要があります。EL3に多くの機能を集める構成は製品向けには慎重に扱うべきです。

### B案：既製ソフトウェアを利用する構成

```text
通常アプリ（Non-secure EL0）
       │
Linux（Non-secure EL1）
       │
       │ OP-TEEクライアント／ドライバ等
       ▼
TF-A等のEL3ランタイム（世界間の切り替え）
       │
       ▼
OP-TEE OS（Secure EL1）
       │
       └─ Trusted Application：鍵操作、署名等

SoCハードウェア：TrustZone属性／XMPU等
```

**利点**：一般的なSecureサービスの実行基盤やAPIを再利用しやすく、機能が増えるほど利点が大きくなります。  
**課題**：起動チェーン、各コンポーネントの移植・設定、セキュリティ更新、SoC対応状況の確認が必要です。導入しただけで認証や鍵保護が完成するわけではありません。

**判断基準**：OSの有無だけで決めず、必要なSecureサービス数、保守期間、第三者コードの利用、攻撃者の能力、認証・鍵管理の要件を基に選定します。

## 5. 認証・認可・鍵管理は何を自作するのか

### 認証と認可の区別

- **認証（Authentication）**：相手や要求の正当性を確かめること。
- **認可（Authorization）**：その相手・要求に、指定の操作を許すか決めること。
- **Secure Bootでの署名検証**：起動するソフトウェアの真正性・完全性を検証すること。SMC要求の認証とは別の論点です。

固定されたベアメタルアプリだけが動き、変更不能であるという前提なら、ユーザー向けログイン機構は不要な場合があります。しかし、Non-secure側が侵害される前提では、**Non-secureからのSMC要求は信用しない**設計が必要です。単に「正規アプリを名乗る」だけでは安全な認証になりません。

### 鍵をどこに置くか

鍵の生成、保管、使用、更新、消去、バックアップ可否を脅威モデルに基づいて決めます。候補はSecure DDR、適切に保護したオンチップメモリ、SoCのeFUSE／PUF等のハードウェア機能です。ただし、機能の利用条件と対応範囲は対象SoC・起動構成で確認する必要があります。

**推奨する設計原則**：秘密鍵をNon-secure側へ渡さず、Secure側で署名等を実行し、結果だけを返す。併せて、Secureサービスの入力検証、権限判定、呼び出し回数・対象操作の制限を検討します。

## 6. 今後の実施順序

| 優先 | 実施項目 | 完了条件 |
|---|---|---|
| 1 | XMPUのアクセス拒否検証 | Secure側の読み書きを維持し、Non-secure側の対象DDRアクセスだけが拒否されることを観測する |
| 2 | 例外・違反原因の照合 | CPUの例外情報とXMPU側の違反情報を突き合わせる |
| 3 | 最小SMCサービス | Non-secure→EL3→Non-secureの往復、引数検証、正常／異常応答を確認する |
| 4 | 脅威モデルの策定 | 攻撃者の権限、保護資産、信頼境界、想定攻撃を定義する |
| 5 | 鍵管理・認可の試作 | 秘密鍵を露出させず、許可された操作のみを実行できることを確認する |
| 6 | 実装方式の選定 | 自作最小構成／TF-A／OP-TEE等の採否を、製品要件で判断する |
| 7 | 製品化要件の検証 | Secure Boot、更新、デバッグ制限、障害時復旧等を評価する |

**直近の最重要課題**：XMPUの設定レジスタを読み戻せたことと、実際にアクセスを拒否できることは別です。保護の実効性を検証するまでは、秘密情報の隔離が成立したとは判断しません。

## 7. 上司と合意したい論点

1. **目的**：TrustZoneの原理実証か、実製品に組み込むSecureサービスの構築か。
2. **守る対象**：秘密鍵、認証情報、ファームウェア、設定値、処理結果のどれか。
3. **攻撃者の前提**：Non-secureアプリ改変、OS侵害、物理アクセス、JTAG利用まで想定するか。
4. **ソフトウェア構成**：ベアメタル継続か、Linux／RTOS導入予定か。Secureサービスの規模はどの程度か。
5. **既製ソフトウェアの採否**：TF-AやOP-TEEを使う理由は何か。機能・保守・認証要件に見合うか。
6. **鍵のライフサイクル**：製造時書き込み、初回起動時生成、更新、失効、故障交換時の扱い。
7. **完成の定義**：実験成功、社内PoC、量産可能なセキュリティ水準のどこを目指すか。

## 8. 説明時の短い結論

> 現在はZCU106のベアメタル環境でTrustZoneを直接制御し、Secure／Non-secureの遷移、DDRアクセス、XMPU設定、例外観測まで確認しています。次の課題はXMPUによる実際のアクセス拒否の実証です。
>
> OP-TEEなどの既製Trusted OSはTrustZone利用の必須条件ではありません。必要なSecure Monitor機能や認証・認可・鍵管理は自作も可能です。ただし、ベアメタルだから認証・認可が不要ということではなく、保護したい資産と攻撃者の前提で必要性が決まります。
>
> まずハードウェア分離を実証し、その後、SMCによる最小Secureサービスを試作したうえで、将来のOS利用や保守要件に応じてTF-A／OP-TEEの採否を判断したいと考えています。

### 用語・参考資料

- **SoC**：System on Chip。CPU、メモリ制御、周辺回路等を集積した半導体。
- **SMC**：Secure Monitor Call。通常側からEL3のモニターを呼び出すためのArm命令。
- **ERET**：例外から復帰するArm命令。
- **TF-A**：Trusted Firmware-A。Arm向けのセキュアファームウェア実装。
- **OP-TEE**：Open Portable Trusted Execution Environment。TrustZoneを利用するTrusted OS実装。
